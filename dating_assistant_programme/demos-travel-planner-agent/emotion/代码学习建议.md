这是一个典型的 **LangChain RAG 服务**：建库 → 检索 → 记忆 → 编排分流。和约会助手用 LangGraph（状态机 + HITL）不同，这里用的是 **Runnable 管道 + RunnableBranch**，没有图节点。按下面顺序读最快。

## 推荐阅读顺序

### 1. `__init__.py`（2 分钟）
先看包职责一览，建立目录地图：

```
indexing/     建库：PDF → 切分 → Chroma
retrieval.py  检索：嵌入模型 + MultiQueryRetriever
memory.py     记忆：Redis 多轮历史
prompts.py    提示词：路由 / RAG / 直答
reports.py    报告：会话 → Markdown → PDF
service.py    编排：RunnableBranch 分流
```

上层只认 `emotion_service`（见 `api/emotion_routes.py`）。

### 2. `service.py`（核心，约 25 分钟）
`EmotionRagService` 是情感咨询的“大脑”。先读 `stream_chat`，再回头看三条链怎么懒加载。

一次对话的分流：

```
stream_chat(thread_id, message)
  ├→ 关键词命中「生成恋爱报告」？
  │     → 读 Redis 历史 → 流式写 Markdown → PDF → report 事件
  ├→ 向量集合已建好？
  │     ├→ 是：RunnableBranch(路由 yes→RAG 链 / 默认→直答链)
  │     └→ 否：一律直答（避免 Collection does not exist）
  └→ SSE 事件：ready → delta* → (report?) → done | error
```

三条链（懒加载，首次用到才建）：

| 方法 | 做什么 |
|------|--------|
| `_rag_condition` | Prompt → LLM → yes/no → bool |
| `_rag_chain_with_history` | 多查询检索 → stuff 进 prompt → 流式作答 + Redis 记忆 |
| `_direct_chain_with_history` | 不检索，靠历史直接回复 + Redis 记忆 |

和约会助手对比记住一句：**那边是图节点改 state；这边是 `|` 管道拼链，记忆靠 Redis 消息列表，不是 MemorySaver checkpoint。**

### 3. `retrieval.py`（10 分钟）
对话侧怎么查书：

- `emotion_collection_exists()`：建库守卫，集合不存在就别构造检索器
- `create_embedding_model()`：文本 → 向量（DashScope OpenAI 兼容）
- `create_multi_query_retriever()`：LLM 把问题改写成多个角度再检索、合并去重

注意：`create_collection_if_not_exists=False`，空集合不会偷偷建出来。

### 4. `memory.py`（5 分钟）
多轮对话怎么“记住”：

- `chat_history(thread_id)` → `RedisChatMessageHistory`
- `trim_input_history` → 只保留最近 N 条，控制上下文长度

对比：约会助手的 `MemorySaver` 存整图 checkpoint（支持 interrupt/resume）；这里只存聊天消息。

### 5. `prompts.py`（需要时再看）
改文案主要改这里，不动链编排：

| 常量 | 角色 |
|------|------|
| `RAG_ROUTE_PROMPT` | 要不要查库（只输出 yes/no） |
| `RAG_SYSTEM_PROMPT` | 基于书籍作答 + 标注来源（含 `{context}`） |
| `DIRECT_SYSTEM_PROMPT` | 寒暄 / 情绪承接，不编造书中观点 |
| `DOCUMENT_PROMPT_TEMPLATE` | 单个检索片段如何格式化 |

### 6. `reports.py`（报告分支再读）
不走 RAG，只基于会话总结：

1. 格式化最近消息 → LLM 流式生成 Markdown  
2. reportlab 渲染 PDF 落盘  
3. `LoveReport` + `find_report_file` 供下载接口查找  

### 7. `indexing/`（建库流水线，约 15 分钟）
对话前要先建索引。调用链：

```
build_indexes(book_name)
  → candidate_book_paths / load_book_documents   # loader
  → split_book_documents                         # splitter（清洗 + 切分）
  → Chroma.from_documents                        # service（向量化写入）
```

| 文件 | 职责 |
|------|------|
| `loader.py` | 发现书目录、PDF → Document（带 book_name 等 metadata） |
| `splitter.py` | 去水印/噪声 → RecursiveCharacterTextSplitter |
| `service.py` | 清旧集合、批量写入 Chroma，对外导出 `build_indexes` |

---

## 一句话心智模型

> **先建库（indexing）→ 对话时路由要不要检索（service）→ 要则 MultiQuery 查 Chroma，不要则直答；全程 Redis 记多轮；要报告则会话总结成 PDF。编排用 LangChain Runnable，不是 LangGraph。**

若只想最快建立全局观：`__init__.py` → `service.py` 的 `stream_chat` + 三条链方法 → `retrieval.py` / `memory.py`，大约 40 分钟就能摸清主链路；建库细节和报告生成遇到再建索引/下载报告时再下钻。
