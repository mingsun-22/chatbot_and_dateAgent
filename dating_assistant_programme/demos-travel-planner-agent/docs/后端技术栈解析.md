# demos-travel-planner-agent 后端技术栈解析

> 本文档聚焦 **Python 后端**（不含 `web/` 前端），基于当前仓库代码与 `requirements.txt` 整理。

## 1. 项目定位

`demos-travel-planner-agent` 是一个 **中文约会助手 + 情感咨询** 双业务后端示例，对外统一由 **FastAPI** 暴露 HTTP 接口。核心业务分为两条线：

| 业务模块 | 包路径 | 编排方式 | 典型能力 |
|---------|--------|---------|---------|
| 约会行程规划 | `agent/` | LangGraph 状态图 | Human-in-the-Loop、并行节点、网页搜索、地图/天气 |
| 情感咨询 | `emotion/` | LangChain Runnable 链 | RAG 检索、Redis 会话记忆、恋爱报告 PDF |

公共能力集中在 `core/`（配置、LLM 工厂）与 `api/`（路由、SSE、请求模型）。

## 4. Web 层：FastAPI + SSE 流式响应

### 4.1 FastAPI / Starlette

- **FastAPI** `0.136.1`：REST API 框架，负责路由注册、请求校验、异常处理。
- **Starlette** `1.0.0`：FastAPI 底层 ASGI 框架。
- **Pydantic** `2.12.5` + **pydantic-settings** `2.14.0`：请求/响应模型与配置校验（见 `api/schemas.py`）。

入口文件 `api/main.py`：

- 创建 `FastAPI` 应用实例；
- 挂载 **CORS 中间件**（`allow_origins=["*"]`，便于本地前后端分离联调）；
- 注册 `emotion_router` 与 `date_router` 两套路由。

### 4.2 流式输出（SSE 风格）

项目未直接使用 `sse-starlette` 装饰器，而是手写 **Server-Sent Events** 格式：

- `api/sse.py` 中 `sse()` 将 JSON 序列化为 `data: {...}\n\n`；
- `FastAPI.responses.StreamingResponse` + `media_type="text/event-stream"` 推送事件流。

约会规划与情感咨询均支持流式：

| 接口 | 事件类型示例 |
|------|-------------|
| `POST /api/date/runs/stream-plan` | `node` / `interrupt` / `final` / `error` |
| `POST /api/emotion/chat/stream` | `ready` / `delta` / `report` / `done` / `error` |

### 4.3 API 路由一览

**约会规划**（`api/date_routes.py`，前缀 `/api/date`）：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/threads` | 创建 thread，返回 `threadId` |
| GET | `/threads/{thread_id}/state` | 查询 LangGraph 当前状态 |
| POST | `/runs/stream-plan` | SSE 流式执行图，支持 interrupt/resume |
| POST | `/runs/invoke` | 非流式同步执行（前端可切换） |

**情感咨询**（`api/emotion_routes.py`，前缀 `/api/emotion`）：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/indexes/build` | 离线构建/重建 Chroma 知识库索引 |
| POST | `/threads` | 创建会话 thread |
| POST | `/chat/stream` | 流式对话（RAG 或直连 LLM） |
| GET | `/reports/{report_id}` | 下载恋爱报告 PDF（`FileResponse`） |

## 5. Agent 编排：LangGraph

### 5.1 核心依赖

| 包 | 版本 | 作用 |
|----|------|------|
| **langgraph** | 1.1.10 | 状态图编排引擎 |
| **langgraph-checkpoint** | 4.0.3 | 检查点/会话持久化 |
| **langgraph-prebuilt** | 1.0.13 | 预置图组件 |
| **langgraph-cli / langgraph-api** | 0.4.21 / 0.7.98 | 本地 `langgraph dev` 调试 |

### 5.2 状态图设计（`agent/graph.py`）

- 使用 `StateGraph(DateState, input_schema=..., output_schema=...)` 定义强类型状态；
- 节点函数在 `agent/nodes.py`，状态结构在 `agent/state.py`（`TypedDict`）；

```
stream_plan_run-->_timed_graph_stream-->graph.stream-->graph.py(图如何构建就在这里，重点文件)
把graph.py看懂后，看3个State，每个节点里的逻辑
```

- 图编译：`builder.compile()`（工具链）或 `builder.compile(checkpointer=MemorySaver())`（API 运行时）。

**节点与边**（graph.py)：

```text
START
  → collect_date_details_hitl
  → confirm_departure_hitl
  → research_weather ─────────────┐
  → summarize_transport_options---------------------------│
  → ask_preferences ──────────────┼→ research_activities ─┐
       └→ research_restaurants--------------------------  |
                                                            ▼
                                              assemble_date_plan → END
```

- **并行扇出**：`confirm_departure_hitl` 后同时进入天气、交通、偏好三个分支；
- **并行汇聚**：`research_activities`、`research_restaurants`、`summarize_transport_options` 全部完成后才进入 `assemble_date_plan`。

### 5.3 Human-in-the-Loop（interrupt / resume）

- 节点内调用 `langgraph.types.interrupt(prompt)` 暂停图执行，向前端抛出追问文案；
- API 层通过 `stream_mode="updates"` 监听 `__interrupt__` 字段（`api/sse.py`）；
- 用户回复后，请求体携带 `command.resume`（封装为 `langgraph.types.Command`）恢复执行。

涉及 interrupt 的节点：

- `collect_date_details_hitl`：收集地点、日期、时间段；
- `confirm_departure_hitl`：确认出发地；
- `ask_preferences`：收集约会偏好。

### 5.4 检查点（Checkpoint）

- `api/date_routes.py` 使用 `langgraph.checkpoint.memory.MemorySaver` 做 **内存级** thread 状态保存；
- 通过 `config={"configurable": {"thread_id": thread_id}}` 隔离多用户会话；
- 支持 `graph.get_state()` 查询、`Command(resume=...)` 续跑。

## 7. 外部服务与工具集成

### 7.1 Tavily 网页搜索

- 包：`langchain-tavily` / `tavily-python`
- 客户端：`agent/clients.py` → `TavilySearch(max_results=4)`
- 用途：搜索约会活动、餐厅等候选信息，结果经 LLM 摘要后写入状态。

### 7.2 高德地图（AMap）REST API

- HTTP 客户端：**httpx** `0.28.1`（同步 `httpx.Client`）
- 配置：`AMAP_API_KEY`、`MAP_TIMEOUT_SECONDS`
- 封装函数（`agent/clients.py`）：

| 函数 | 高德接口 | 用途 |
|------|---------|------|
| `map_geocode_detail` | `/v3/geocode/geo` | 地点 → 经纬度、adcode |
| `map_weather_forecast` | `/v3/weather/weatherInfo` | 目标城市天气预报 |
| `map_transit_route_summary` | `/v3/direction/transit/integrated` | 公交路线摘要 |

### 7.3 Chroma 向量数据库（情感 RAG）

- 包：**chromadb** `1.5.9` + **langchain-chroma** `1.1.0`
- 部署模式：**HttpClient** 连接远程 Chroma 服务（`CHROMA_HOST` / `CHROMA_PORT`）
- 集合名：`emotion_books`（可配置）
- 嵌入模型：DashScope `text-embedding-v3`（`OpenAIEmbeddings`，维度 1024）

### 7.4 Redis 会话记忆

- 包：**redis** `5.2.1`
- 集成：`langchain_community.chat_message_histories.RedisChatMessageHistory`
- 配置项：
  - `REDIS_URL`
  - `EMOTION_REDIS_KEY_PREFIX`
  - `EMOTION_MEMORY_TTL_SECONDS`（默认 7 天）
  - `EMOTION_MEMORY_WINDOW_MESSAGES`（默认保留最近 20 条）

## 8. 情感咨询：RAG 知识库流水线

### 8.1 离线索引构建

路径：`emotion/indexing/`

```text
PDF 书籍 (data/emotion_books/)
    → PyPDFLoader 按页加载
    → 文本清洗 / 水印过滤 (splitter.py)
    → RecursiveCharacterTextSplitter 切分 (1200 字块, 120 重叠)
    → OpenAIEmbeddings 向量化
    → 写入 Chroma 集合
```

触发接口：`POST /api/emotion/indexes/build`

### 8.2 在线检索增强生成

路径：`emotion/retrieval.py` + `emotion/service.py`

1. **路由判断**：LLM 根据用户问题输出 yes/no，决定是否走 RAG（`RAG_ROUTE_PROMPT`）；
2. **MultiQueryRetriever**：将用户问题改写成 3 个检索 query，提高召回率；
3. **Stuff Documents Chain**：将 Top-K 文档片段塞入 prompt，流式生成回答；
4. **直连分支**：不走检索时，仅用系统提示词 + Redis 历史对话。

### 8.3 恋爱报告生成

路径：`emotion/reports.py`

| 技术 | 用途 |
|------|------|
| LLM 流式生成 | 将会话历史转为 Markdown 报告 |
| **ReportLab** `4.4.5` | Markdown → PDF 排版输出 |
| 本地文件系统 | `data/emotion_reports/` 存储，API 提供下载 |

## 9. 中文 NLP 与数据处理

| 技术 | 包 | 用途 |
|------|-----|------|
| **JioNLP** | jionlp `1.5.28` | 中文自然语言日期解析（`agent/date_parser.py`） |
| **PyPDF** | pypdf `6.10.2` | PDF 文本提取（经 LangChain PyPDFLoader） |
| **正则表达式** | Python `re` | 时间段解析、搜索摘要截断、PDF 噪声过滤 |

日期解析策略：

- 时区固定为 `Asia/Shanghai`（UTC+8）；
- 调用 `jio.parse_time()` 解析「今天/明天/下周六」等相对日期；
- 结构化日期字段再由 LLM `with_structured_output` 抽取与校验。

## 16. 如何学习本项目后端源码（讲课导读）

> 本节给出一条从"跑起来"到"读透每个模块"的完整路径，配合精确的文件/函数锚点，能顺着一次真实请求把整条链路串起来，而不是孤立地看某个文件。

### 16.0 学习总原则：不要从第一行代码读起

读一个 Agent 后端项目，最忌讳打开 `agent/nodes.py` 从头往下啃。正确姿势是**「三遍法」**：

1. **第一遍（跑）**：先把服务跑起来，用浏览器/前端点一遍两个功能，建立"输入 → 输出"的直觉；
2. **第二遍（追）**：抓住**一次请求**，顺着"路由 → 服务/图 → 客户端 → 外部服务"的调用链跳读，只看主干、跳过细节；
3. **第三遍（拆）**：再按模块逐个精读实现细节（prompt、解析、切分、检索重写等）。

建议严格这三遍推进，每一遍心里都有"这块代码在整条链路的哪个位置"的坐标感。

### 16.1 前置准备（第 0 步）

| 准备项 | 说明 | 参考 |
|--------|------|------|
| 读架构图 | 先看 `docs/course/01-项目综述说明.md` 的 mermaid 架构图，记住 `api → emotion/agent → 外部服务` 三层 | 课程文档 |
| 配好 `.env` | 复制 `.env.example` 为 `.env`，填 Qwen/Tavily/高德 key，启动 Chroma 与 Redis | 见第 10 节 |
| 启动后端 | `uvicorn api.main:app --reload --port 8000`，打开 `http://127.0.0.1:8000/docs` 看自动生成的接口文档 | `api/main.py` |
| 备好断点 | 在 PyCharm 里对着 `api/main.py:app` 起一个 debug 配置，后面追代码时随时打断点 | — |

**讲课要点**：`/docs`（Swagger UI）是最好的"上帝视角"，先让学员在这里看到 4+4 个接口，再去读代码，就知道"代码最终是为了实现这些接口"。

### 16.2 推荐阅读顺序（由外到内、由公共到业务）

按下面的顺序读，每个文件都建立在前一个的基础上，认知负担最小：

```text
第 1 层 公共基座（最先读，其他所有模块都依赖它）
  core/settings.py   →  配置怎么从 .env 进来
  core/llm.py        →  全项目怎么统一拿到一个 LLM 客户端（工厂方法）

第 2 层 入口与协议（搞懂请求怎么进来、流式怎么出去）
  api/main.py        →  app 怎么创建、路由怎么挂载（10 行，最好的起点）
  api/schemas.py     →  请求体长什么样（Pydantic 模型）
  api/sse.py         →  SSE 格式 + interrupt 解析 + resume 输入（三个小工具函数）

第 3 层 业务主线 A：约会规划（LangGraph 工作流）
  api/date_routes.py →  4 个接口 + graph.stream 的驱动方式
  agent/state.py     →  状态字典结构（DateState，先看数据再看逻辑）
  agent/graph.py     →  节点怎么连成图（边的顺序 = 业务顺序）
  agent/nodes.py     →  每个节点干什么（最后读，也是最厚的一个）
  agent/clients.py   →  Tavily / 高德 / LLM 客户端封装
  agent/date_parser.py + agent/prompts.py  →  细节工具

第 4 层 业务主线 B：情感咨询（LangChain 链 + RAG）
  api/emotion_routes.py    →  4 个接口，逻辑极薄，全委托给 service
  emotion/service.py       →  RAG/直答/报告 三条链的编排（情感模块的大脑）
  emotion/memory.py        →  Redis 会话记忆与窗口裁剪
  emotion/retrieval.py     →  Chroma + MultiQueryRetriever 查询重写
  emotion/indexing/*.py    →  离线建库：loader → splitter → service
  emotion/reports.py + prompts.py  →  报告生成与提示词
```

**讲课节奏建议**：一次课先讲第 1、2 层 + 主线 A（约会规划闭环），下一次课再讲主线 B（情感咨询 + RAG），因为主线 B 涉及向量库/检索重写，概念更重。

### 16.3 核心手法：追一次请求的完整生命周期

这是本节最重要的部分。带学员**顺着调用链跳读**，而不是逐文件读。

#### 链路 A：约会规划一次"提问 → 中断 → 恢复"

```text
① 前端 POST /api/date/threads
      → api/date_routes.py:create_thread()      生成 threadId（uuid）

② 前端 POST /api/date/runs/stream-plan { threadId }
      → api/date_routes.py:stream_plan_run()     入口，返回 StreamingResponse
      → _timed_graph_stream()                    包一层耗时日志后驱动 graph.stream(...)
      → api/sse.py:stream_input()                首次运行 → 返回空输入 {}
      → agent/graph.py:graph.stream(...)         按边执行：collect_date_details_hitl 先跑
      → agent/nodes.py:collect_date_details_hitl 调 interrupt("请告诉我约会地点…") 暂停
      → api/sse.py:extract_interrupt_value()     从 chunk 里识别 __interrupt__
      → stream_plan_run 推送 {"type":"interrupt", value, values}  然后 return 结束本次流

③ 前端把用户回答再 POST /api/date/runs/stream-plan { threadId, command:{resume:"…"} }
      → api/sse.py:stream_input()                这次带 command → 返回 Command(resume=…)
      → LangGraph 从上次 interrupt 处继续，走 confirm_departure_hitl → ask_preferences
      → 之后扇出并行：research_weather / summarize_transport_options / research_restaurants
      → 汇聚到 assemble_date_plan → END
      → 推送 {"type":"final", values:{agenda:…}}  前端渲染方案卡片
```

**追这条链时务必强调的三个"啊哈"点**：

1. **状态是怎么攒起来的**：每个节点 `return {字段:值}`，LangGraph 自动合并进 `DateState`（`agent/state.py`），下个节点用 `state.get(...)` 取。让学员对着 `state.py` 的字段看，就明白节点之间靠状态字典"接力"。
2. **中断/恢复的本质**：`interrupt()` 抛出后靠 `MemorySaver`（`date_routes.py:32` 编译时传入）保存现场，`thread_id` 决定读写哪段现场；`Command(resume=…)` 让图从断点续跑——这就是 Human-in-the-Loop。
3. **为什么三个 `_hitl` 节点必须串行**：`agent/graph.py` 里有一段很长的注释解释——带 `interrupt` 的节点若放进并行分支，恢复时会重跑整个并行超级步，导致时序错乱。这是讲"并行 + 中断"陷阱的最佳真实案例。

#### 链路 B：情感咨询一次"带 RAG 的流式对话"

```text
① 前端 POST /api/emotion/chat/stream { threadId, message }
      → api/emotion_routes.py:stream_emotion_chat()   薄路由，遍历 service 产出的事件包成 SSE
      → emotion/service.py:EmotionRagService.stream_chat()   情感模块大脑

② stream_chat 内部按"三个分支"决策：
   分支1 是否生成报告  _is_report_requested() 命中关键词 → 走 reports.py 生成 PDF
   分支2 集合是否存在  emotion_collection_exists()  未建库 → 直接走直答链（避开 Chroma 报错）
   分支3 是否需要 RAG  RunnableBranch + _rag_condition()  让 LLM 判断 yes/no

③ 若走 RAG：_rag_chain_with_history()
      → emotion/retrieval.py:create_multi_query_retriever()  一个问题改写成多个 query 提升召回
      → Chroma 检索 Top-K 片段 → create_stuff_documents_chain 塞进 prompt
      → RunnableWithMessageHistory 自动读写 Redis 历史（emotion/memory.py）
      → llm.stream(...) 流式产出 → 逐块 yield {"type":"delta", text}
```

**追这条链时的"啊哈"点**：

1. **RunnableBranch = if/else 的链式写法**：`service.py:106` 那段 `RunnableBranch((条件, A), B)` 就是"条件成立走 A 链，否则走 B 链"，是 LangChain 声明式编排的典型。
2. **会话记忆是"包"上去的**：`RunnableWithMessageHistory` 把一条普通链包一层，就自动获得"运行前读历史、运行后写历史"的能力，key 是 `session_id`（即 threadId）。对照 Java 的 `RedisTemplate` 手写读写，体会声明式的差异。
3. **懒加载缓存**：三条链都用 `self._xxx_chain is not None` 做缓存，首次用到才构建——讲"为什么构造链有成本、要复用"。

### 16.4 关键概念的代码锚点（速查表）

带学员读时，遇到抽象概念可直接跳到这些精确位置看"活代码"：

| 概念 | 一句话理解 | 代码锚点 |
|------|-----------|---------|
| ASGI 应用入口 | `app` 就是被 uvicorn 加载的对象 | `api/main.py:20` |
| SSE 流式协议 | `data: {...}\n\n` 一条事件 | `api/sse.py:sse()` |
| LangGraph 状态 | 节点间接力的数据字典 | `agent/state.py:DateState` |
| 图 = 节点 + 边 | 边的顺序就是业务顺序 | `agent/graph.py:70-92` |
| Human-in-the-Loop | `interrupt()` 暂停 + `Command(resume=)` 续跑 | `agent/nodes.py` 各 `_hitl` 节点 / `api/sse.py:stream_input()` |
| 检查点持久化 | `MemorySaver` + `thread_id` 隔离会话 | `api/date_routes.py:32,46` |
| 结构化输出 | 让 LLM 严格按 Pydantic 字段返回 | `agent/nodes.py` `with_structured_output(...)` |
| RunnableBranch | 声明式 if/else 选链 | `emotion/service.py:106` |
| RAG 检索链 | 检索片段填 context 再生成 | `emotion/service.py:_rag_chain_with_history()` |
| 查询重写 | 一问改多问提升召回 | `emotion/retrieval.py:create_multi_query_retriever()` |
| 会话记忆 | Redis 历史 + 窗口裁剪 | `emotion/memory.py` |
| 离线建库 | 加载 → 清洗切分 → 向量化入库 | `emotion/indexing/service.py` |

### 16.5 动手实验（让学员在读中改、在改中懂）

光读不动手记不牢。建议穿插这些小实验：

1. **加一条日志看状态流转**：在 `agent/nodes.py` 某个节点开头 `print(state.keys())`，跑一次约会规划，观察状态字段是怎么一步步变多的。
2. **改一条边观察时序**：临时把 `agent/graph.py` 里 `research_weather → research_activities` 改动，看方案质量/报错变化，理解"边即依赖"。
3. **关掉 RAG 看差异**：把 `emotion/service.py` 的 `_rag_condition` 强制返回 False，对比"带书籍引用"和"纯直答"的回答差异，直观感受 RAG 的价值。
4. **看耗时日志**：约会规划接口内置了 `date_agent.timing` 耗时日志（`date_routes.py:_log_timing`），跑一次后看控制台每个节点耗时，理解并行分支为什么能省时间。
5. **用 `/docs` 直接发请求**：不依赖前端，在 Swagger UI 里对 `/api/date/threads`、`/runs/stream-plan` 手工发请求，看原始 SSE 返回，彻底搞懂协议。
6. **可选：`langgraph dev` 可视化**：项目带 `langgraph.json`，执行 `langgraph dev` 可在浏览器里可视化 `travel_planner` 图的节点与执行流，非常适合课堂演示"图长什么样"。

### 16.6 读源码时容易踩的坑 / 常见疑问

| 疑问 | 解答 |
|------|------|
| 节点返回的字典怎么就"进"状态了？ | LangGraph 框架自动把返回值 merge 进 `DateState`，无需手动赋值 |
| 为什么进程重启会话就没了？ | 用的是 `MemorySaver`（内存检查点），教学够用；生产可换 Redis/Postgres checkpointer |
| RAG 链找不到集合报错怎么回事？ | `emotion/service.py:104` 特意先判断 `emotion_collection_exists()`，没建库就走直答链，避开 Chroma 抛错 |
| `with_structured_output` 是魔法吗？ | 它让 LLM 按 Pydantic schema 输出并自动解析，省去手写 JSON 解析和容错 |
| 为什么很多链都懒加载？ | 构造链（尤其带检索器）有开销，用 `is not None` 缓存复用 |

### 16.7 一句话串讲（课堂收尾用）

> 前端发请求 → `api/` 路由接住并决定"流式还是同步" → 约会规划交给 `agent/` 的 **LangGraph 图**（节点接力 + 中断/恢复 + 并行），情感咨询交给 `emotion/` 的 **LangChain 链**（路由 → RAG/直答 → Redis 记忆）→ 两者最终都调 `core/` 的统一 LLM 与外部服务（Tavily/高德/Chroma）→ 结果以 **SSE** 一段段推回前端。

抓住了整个后端的骨架，剩下的都是往骨架上填细节。
