# 情感咨询功能源码预习

本文件只整理情感咨询功能相关源码，用于配合 `02-情感咨询功能说明.md`，以及 `后端技术栈解析.md` 中和情感 RAG 相关的章节进行预习。

重点关注三条主线：

```text
1. 离线建库：书籍 PDF -> 清洗切分 -> 向量化 -> Chroma
2. 在线问答：用户问题 -> 判断 RAG/直答 -> 检索 -> LLM 流式回答
3. 会话/报告：Redis 保存多轮记忆，必要时生成恋爱报告 PDF
```



## 1. 情感咨询入口

情感咨询 HTTP 接口都在：

```text
api/emotion_routes.py
```

它提供 4 个接口：

```text
POST /api/emotion/indexes/build
POST /api/emotion/threads
POST /api/emotion/chat/stream
GET  /api/emotion/reports/{report_id}
```

最核心的是流式聊天接口：

```python
@router.post("/chat/stream")
def stream_emotion_chat(req: EmotionChatRequest) -> StreamingResponse:
    if not req.threadId:
        raise HTTPException(status_code=400, detail="threadId required")

    def event_stream():
        for event in emotion_service.stream_chat(req.threadId, req.message):
            yield sse(event)

    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

这段代码的含义：

```text
前端传 threadId + message
-> 路由层不处理业务
-> 交给 emotion_service.stream_chat()
-> service 每产出一个事件
-> 用 sse() 包成 data: {...}\n\n
-> 前端边收边展示
```

所以 `api/emotion_routes.py` 类似 SpringMVC Controller，真正业务在：

```text
emotion/service.py
```

### 2.4 清洗和切分

清洗切分在：

```text
emotion/indexing/splitter.py
```

入口函数：

```python
def split_book_documents(
    documents: list[Document],
    max_chars: int = 1200,
    overlap_chars: int = 120,
) -> list[Document]:
```

先清洗：

```python
text = normalize_extracted_text(document.page_content)
if not text or is_noise_chunk(text):
    continue
```

清洗函数：

```python
def normalize_extracted_text(text: str) -> str:
    normalized = str(text or "")
    for pattern in WATERMARK_PATTERNS:
        normalized = re.sub(pattern, "", normalized, flags=re.IGNORECASE)
    normalized = re.sub(r"(?<=[\u4e00-\u9fff])[ \t]+(?=[\u4e00-\u9fff])", "", normalized)
    normalized = re.sub(r"[ \t\r\f\v]+", " ", normalized)
    normalized = re.sub(r"\n{3,}", "\n\n", normalized)
    return normalized.strip()
```

做了几件事：

```text
去水印
去掉中文之间多余空格
压缩连续空白
压缩连续空行
```

再切分：

```python
splitter = RecursiveCharacterTextSplitter(
    chunk_size=max_chars,
    chunk_overlap=overlap_chars,
    separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
)
```

关键参数：

```text
chunk_size = 1200
chunk_overlap = 120
```

含义：

```text
每个片段大约 1200 字
相邻片段重叠 120 字
```

重叠是为了避免一句话刚好被切断，导致检索时上下文丢失。

## 3. 在线 RAG 流式对话

对应后端技术栈解析中和情感咨询相关的：

```text
16.3 链路B：情感咨询一次带 RAG 的流式对话
```

完整链路：

```text
POST /api/emotion/chat/stream
-> api/emotion_routes.py:stream_emotion_chat()
-> emotion/service.py:stream_chat()
-> 判断报告 / 判断知识库 / 判断是否 RAG
-> RAG: retrieval.py 检索 Chroma
-> service.py 拼 prompt + history
-> Qwen 流式生成
-> SSE 返回 delta
```

### 3.1 stream_chat 总调度

核心函数在：

```text
emotion/service.py
```

```python
def stream_chat(self, thread_id: str, message: str) -> Iterable[dict[str, Any]]:
```

它先清理输入：

```python
clean_message = message.strip()

if not clean_message:
    yield {"type": "error", "message": "消息不能为空!"}
    return
```

然后先发开始事件：

```python
yield {"type": "ready"}
```

前端收到 `ready`，就知道后端已经开始处理。

### 3.2 第一分支：是否生成报告

判断函数：

```python
def _is_report_requested(self, message: str) -> bool:
    keywords = ("生成报告", "下载报告", "导出报告", "恋爱报告", "关系报告", "情感报告", "恋爱分析文档")
    return any(keyword in message for keyword in keywords)
```

只要命中这些关键词，就走报告分支，不走普通 RAG 问答。

### 3.3 第二分支：Chroma 集合是否存在

代码：

```python
if emotion_collection_exists():
    chain = RunnableBranch(
        (self._rag_condition(), self._rag_chain_with_history()),
        self._direct_chain_with_history(),
    )
else:
    chain = self._direct_chain_with_history()
```

这段有三个层次：

```text
1. Chroma 集合不存在
   -> 直接走直答，避免报错

2. Chroma 集合存在，但用户只是“谢谢”
   -> _rag_condition() 返回 False，走直答

3. Chroma 集合存在，用户提出新的情感问题
   -> _rag_condition() 返回 True，走 RAG
```

判断 Chroma 集合是否存在：

```text
emotion/retrieval.py
```

```python
def emotion_collection_exists() -> bool:
    try:
        client = chroma_client()
        client.get_collection(settings.emotion_collection_name)
        return True
    except Exception:
        return False
```

这个守卫很重要。否则 Chroma 集合没建好时，一检索就会报：

```text
Collection [emotion_books] does not exist
```

### 3.4 第三分支：是否需要 RAG

判断链在：

```text
emotion/service.py
```

```python
self._rag_condition_chain = prompt | llm | StrOutputParser() | RunnableLambda(
    lambda text: str(text).strip().lower().startswith("yes")
)
```

这是 LangChain 的 LCEL 管道写法：

```text
Prompt
-> LLM
-> 转字符串
-> 判断是不是 yes 开头
```

提示词在：

```text
emotion/prompts.py
```

`RAG_ROUTE_PROMPT` 要求模型只输出：

```text
yes 或 no
```

也就是说，不是每句话都查知识库。比如：

```text
“谢谢”
“我明白了”
“好的”
```

这类输入就没有必要走 RAG。

## 4. RAG 链内部怎么跑

RAG 链在：

```text
emotion/service.py
```

函数：

```python
def _rag_chain_with_history(self) -> RunnableWithMessageHistory:
```

### 4.1 构造 RAG prompt

```python
prompt = ChatPromptTemplate.from_messages(
    [
        ("system", RAG_SYSTEM_PROMPT),
        MessagesPlaceholder("history"),
        ("human", "{input}"),
    ]
)
```

这三部分分别是：

```text
RAG_SYSTEM_PROMPT       系统提示词，里面有 {context}
history                 Redis 里的历史消息
input                   用户当前问题
```

### 4.2 创建文档拼接链

```python
stuff_chain = create_stuff_documents_chain(
    llm,
    prompt,
    document_prompt=document_prompt,
    document_separator="\n\n",
    document_variable_name="context"
)
```

`create_stuff_documents_chain` 的作用：

```text
把检索到的多个 Document
格式化成文本
塞进 prompt 的 {context}
```

每个 Document 的格式来自：

```text
emotion/prompts.py
```

```text
DOCUMENT_PROMPT_TEMPLATE
```

模板内容：

```text
资料来源：
书籍：《{book_name}》
文件：{file_name}
页码：{page_start}-{page_end}

内容：
{page_content}
```

所以 RAG 最终给模型的上下文不是裸文本，而是带来源信息的文本。

### 4.3 创建多查询检索器

代码：

```python
retriever = create_multi_query_retriever(self.similarity_top_k)
```

源码在：

```text
emotion/retrieval.py
```

先连接 Chroma：

```python
vector_store = Chroma(
    collection_name=settings.emotion_collection_name,
    embedding_function=create_embedding_model(),
    host=settings.chroma_host,
    port=settings.chroma_port,
    create_collection_if_not_exists=False,
)
```

再变成 retriever：

```python
base_retriever = vector_store.as_retriever(search_kwargs={"k": top_k})
```

最后包成 `MultiQueryRetriever`：

```python
return MultiQueryRetriever.from_llm(
    retriever=base_retriever,
    llm=llm,
    prompt=MULTI_QUERY_PROMPT,
    include_original=True,
)
```

`MultiQueryRetriever` 的作用：

```text
用户问题
-> LLM 改写成 3 个不同角度的问题
-> 原问题 + 3 个改写问题一起检索
-> 合并去重
```

比如用户问：

```text
她总是忽冷忽热，我是不是该继续主动？
```

可能会被改写成：

```text
如何判断暧昧对象忽冷忽热的真实意图
恋爱关系中一方回应不稳定时如何沟通
追求阶段主动与退后的边界如何把握
```

这样比单次检索更容易召回相关片段。

### 4.4 组装 RAG 链

核心代码：

```python
rag_chain = RunnablePassthrough.assign(
    context=(lambda values: values["input"]) | retriever
) | stuff_chain
```

翻译成流程：

```text
原始输入里有 input
-> 取出 input 给 retriever
-> retriever 返回 Document 列表
-> 把 Document 列表放到 context 字段
-> stuff_chain 把 context + history + input 交给 LLM
```

## 5. Redis 会话记忆

RAG 链外面又包了一层：

```python
self._rag_chain = RunnableWithMessageHistory(
    RunnableLambda(trim_input_history) | rag_chain,
    chat_history,
    input_messages_key="input",
    history_messages_key="history",
)
```

这段是情感咨询多轮对话的核心。

### 5.1 Redis 历史对象

代码在：

```text
emotion/memory.py
```

```python
def chat_history(thread_id: str) -> RedisChatMessageHistory:
    if not settings.redis_url:
        raise RuntimeError("缺少 REDIS_URL。")
    return RedisChatMessageHistory(
        session_id=thread_id,
        url=settings.redis_url,
        key_prefix=settings.emotion_redis_key_prefix,
        ttl=settings.emotion_memory_ttl_seconds,
    )
```

Redis key 大致是：

```text
emotion:chat:{threadId}
```

所以不同 `threadId` 的会话不会串。

### 5.2 历史裁剪

代码：

```python
def trim_input_history(inputs: dict) -> dict:
    values = dict(inputs)
    history = values.get("history")
    if isinstance(history, list):
        values["history"] = history[-settings.emotion_memory_window_messages:]
    return values
```

它只保留最近 N 条消息，默认通常是 20 条。

原因：

```text
模型上下文长度有限
历史太长会增加成本
太久远的内容可能干扰当前问题
```

### 5.3 RunnableWithMessageHistory 的作用

你可以把 `RunnableWithMessageHistory` 理解成给链套了一个“记忆外壳”：

```text
调用链之前：
  根据 session_id 读取 Redis 历史
  注入到 history

调用链之后：
  把用户问题和模型回答写回 Redis
```

这比手写 Redis 读写更声明式。

## 6. 直答链

直答链在：

```text

```

```python
def _direct_chain_with_history(self) -> RunnableWithMessageHistory:
```

```python
prompt = ChatPromptTemplate.from_messages(
```


## 7. SSE 流式返回

最终在 `emotion/service.py` 中：

```python
stream = chain.stream(
    {"input": clean_message},
    config={"configurable": {"session_id": thread_id}},
)

for chunk in stream:
    text = _chunk_text(chunk)
    if text:
        yield {"type": "delta", "text": text}

yield {"type": "done"}
```

每一个 `delta` 事件会被路由层包装成 SSE。

包装函数在：

```text
api/sse.py
```

```python
def sse(payload: dict[str, Any]) -> str:
    return f"data: {json.dumps(payload, ensure_ascii=False)}\n\n"
```

前端收到的数据类似：

```text
data: {"type":"ready"}

data: {"type":"delta","text":"我理解你的困惑..."}

data: {"type":"delta","text":"从关系互动看..."}

data: {"type":"done"}
```

这就是前端能够边生成边显示的原因。

## 8. 恋爱报告分支

报告生成在 `stream_chat()` 里优先判断。

只要用户输入命中：

```text
生成报告
下载报告
导出报告
恋爱报告
关系报告
情感报告
恋爱分析文档
```

就走报告分支，不走普通 RAG 问答。

核心代码：

```python
history = chat_history(thread_id)
messages = trim_input_history({"history": history.messages})["history"]

markdown_parts: list[str] = []
for text in stream_report_markdown_from_messages(messages):
    markdown_parts.append(text)
    yield {"type": "delta", "text": text}

report = create_love_report_from_markdown("".join(markdown_parts))
```

报告 Markdown 生成：

```text
emotion/reports.py
stream_report_markdown_from_messages()
```

PDF 落盘：

```text
emotion/reports.py
create_love_report_from_markdown()
```

下载接口：

```text
api/emotion_routes.py
download_emotion_report()
```

流程：

```text
用户说生成恋爱报告
-> 读取 Redis 最近 N 条对话
-> LLM 流式生成 Markdown

-> 返回 report 事件
-> 前端展示下载链接
```

## 9. 复习路径

以后你复习情感咨询功能，按这个顺序打开文件：

```text

2. emotion/service.py
   stream_chat()

5. emotion/service.py
```

## 10. 一句话总结

情感咨询不是“问大模型一句话”，而是 FastAPI 接收请求后，由 `EmotionRagService` 决定走报告、RAG 或直答；RAG 分支会用 `MultiQueryRetriever` 从 Chroma 检索书籍片段，再把片段、Redis 历史和用户问题一起交给 Qwen，最后用 SSE 一段段返回。
