这是一个典型的 **LangGraph 状态机**：状态定义 → 节点实现 → 图装配。按下面顺序读最快。

## 推荐阅读顺序

### 1. `state.py`（5 分钟）
先看状态字段长什么样。`DateState` 就是节点之间传递的“共享黑板”，后面每个节点都在读写这些字段。

重点记住四类字段：
- 基本信息：`date_area` / `date_date` / `date_time_range`
- 地理：出发地、经纬度、`adcode`
- 偏好：`date_preferences`、预算关键词
- 各节点产出：天气、交通、活动、餐饮、最终 `agenda`

### 2. `graph.py`（10 分钟）
看清**执行流程图**，再读节点才不会迷路：

```
START
  → collect_date_details_hitl   # 收集地点/日期/时间
  → confirm_departure_hitl      # 确认出发地
  → ask_preferences             # 问偏好（三个 HITL 必须串行）
      ├→ research_weather → research_activities
      ├→ summarize_transport_options
      └→ research_restaurants
            ↓（三路汇聚）
      assemble_date_plan → END
```

文件里关于「HITL 不能并行」的注释很关键，建议认真读。

### 3. `nodes.py`（核心，按图顺序读）
不要从上到下抠辅助函数，按业务节点走：

| 顺序 | 函数 | 做什么 |
|------|------|--------|
| ① | `collect_date_details_hitl` | interrupt 问用户 → LLM 抽取 → 地理编码 |
| ② | `confirm_departure_hitl` | interrupt 确认出发地 |
| ③ | `ask_preferences` | interrupt 问偏好 |
| ④ | `research_weather` | 高德天气 + LLM 穿搭建议 |
| ⑤ | `summarize_transport_options` | 高德公交路线 |
| ⑥ | `research_activities` / `research_restaurants` | Tavily 搜索 + LLM 整理 |
| ⑦ | `assemble_date_plan` | 汇总成最终方案 |

辅助函数（`_parse_*`、`_compact_*`、`_research_recommendations`）遇到调用再跳进去看即可。

### 4. `clients.py`（需要时再看）
外部能力封装：`llm`、Tavily `search`、高德地理编码/天气/公交。节点里看到 `map_geocode_detail` 等再回来对照。

### 5. `prompts.py` + `date_parser.py`（细节）
- `prompts.py`：每个 LLM 调用“说了什么”，改文案主要改这里
- `date_parser.py`：把「下周六」解析成 `YYYY-MM-DD`，主要在收集信息节点用到

---

## 一句话心智模型

> **状态（state）装数据 → 节点（nodes）改数据 → 图（graph）定顺序；HITL 先串行问完，再并行查天气/交通/餐饮，最后整合。**

若只想最快建立全局观：`state.py` → `graph.py` → `nodes.py` 里那 8 个公开节点函数，大约 30–40 分钟就能摸清主链路。
